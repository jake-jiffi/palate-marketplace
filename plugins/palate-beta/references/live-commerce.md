# Optional Shopify guest commerce

Use this slice when the observed source profile identifies Shopify commerce (`platform`, case-insensitive, is `shopify`, with supporting facts), or the user explicitly chooses Shopify. Service, editorial, portfolio and software marketing projects do not install it. Hybrid projects add only their buying routes. Accounts, subscriptions, bundles, B2B pricing and custom pricing require their own agreed scope. A required selling plan blocks purchase in this guest slice.

After selecting the live design, run `node <plugin>/scripts/install-shopify-overlay.mjs <project> --confirm-shopify`, then `npm install`. The installer refuses existing destinations and adds the Node Vercel runtime to the neutral Astro starter. It leaves the home page for the builder to compose. Adapt `src/layouts/CommerceLayout.astro` to the selected shared layout, tokens, media and motion. Its semantic controls and native forms are the functional starting point, not a finished visual design. Brochure pages stay static. Build any commerce home content from the same current Storefront methods with on-demand rendering and `private, no-store`.

Configure server-only `SHOPIFY_STORE_DOMAIN`, `SHOPIFY_STOREFRONT_TOKEN`, `SHOPIFY_COUNTRY`, `SHOPIFY_REDIS_URL` and a unique `SHOPIFY_REDIS_NAMESPACE`. Use the stable myshopify domain, Storefront API 2026-07, Node 22.12 or newer and the committed lockfile. Redis client 6.2.1 and Vercel adapter 11.0.10 are exact pins. The installer scopes a `path-to-regexp` 6.3.0 override to `@vercel/routing-utils`, removing its vulnerable 6.1.0 dependency; verify the generated lock with `npm audit`, `astro check` and `astro build`. Remote Redis requires native TCP/TLS (`rediss:`), durable storage and atomic EVAL support. Keep its credentials in the deployment environment. Loopback Redis is for local tests. Do not replace the durable journal with process memory or local files on Vercel. Default checkout host is the stable shop domain; explicitly add only verified exact shop checkout hosts if needed.

The overlay reads collection membership, catalogue/search connections, filters, sort and cursors from Shopify. PDP URLs support exact `?variant=` or selected option inputs. No cached catalogue snapshot supplies prices or availability. Zero is a valid price. The server rechecks the exact variant, market and quoted price before adding it. A Shopify stock warning is visible, with reconfirmation required. The cart page lists every line and retains discounts and market during recovery.

Session establishment is a separate round trip before purchase forms become actionable. The browser holds an opaque HttpOnly, SameSite=Lax SID, Secure on HTTPS. Cart capabilities and operation receipts stay in Redis. Mutation endpoints never set a SID cookie. Enhanced bootstrap uses a cross-tab Web Lock where available; no-JavaScript forms follow the same server checks. A form bound to a different session produces an explicit context conflict and an option to continue with that tab's cart. It never merges carts silently.

Each server-issued form token binds a stable operation ID, payload, generation, revision and displayed quote. The journal atomically claims the operation before a Shopify write. Reusing the same operation returns its known receipt; changing its payload or using a stale form fails before another write. An interrupted write remains pending or unknown after worker death, Redis reconnection or restart. A lease expiry is not permission to replay it. The enhanced client retains an unresolved opaque form token and exact input in per-tab session storage, with an in-document fallback if storage is denied. Passive refresh cannot turn it into a new purchase intent. The user can explicitly check that action's receipt or recover their cart. A known success refreshes controls for the next deliberate action. Review the current cart, then explicitly confirm a new cart generation when recovery is needed. Select an available subset or explicitly start empty, preserving the original market and attempted discount codes for rechecking. The retired generation remains in the session journal until expiry, and late workers cannot commit into the replacement. Redis sessions and receipts have a seven-day sliding server expiry.

Checkout uses POST and the same session owner, generation and revision fence as mutations. It reads the latest nonempty cart and validates its market, totals, availability and allowed HTTPS checkout host. Pending or unknown writes cannot redirect to checkout. A changed cart requires explicit confirmation. Recovery reconfirms current item prices, original market and discount results before checkout. The read-only checkout lease can be reclaimed after expiry, but an expired worker cannot complete under a newer owner.

Release evidence must include deterministic hostile journal tests against real Redis, two-process contention and a Redis restart, plus the actual development-store path: collection membership and pagination, exact variant and zero-price item, unavailable variant, add/update/remove, discount result, reload persistence, two tabs, no-JavaScript forms, accessible drawer, and a real checkout handoff that stops before payment. Fixture tests prove fault behaviour, not Shopify compatibility. Verify `shop.plan.partnerDevelopment` through an authenticated read before development-store writes. Do not seed products, alter merchant production data or place orders for this test.
